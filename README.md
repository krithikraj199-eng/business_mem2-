# Member 3: Pairwise Matching & Classification

## 1. System Responsibility & Overview
Member 3 is responsible for the **pairwise matching and classification engine** within the Business Entity Resolution pipeline.

Given candidate pairs generated by Member 2's blocking mechanism and normalized entity records indexed by Member 1, Member 3:
1. Performs disk-backed joins between Source 1 records and candidate targets (Source 2 / Source 3) with bounded RAM usage.
2. Extracts a deterministic 12-feature similarity representation (string distances, character n-gram TF-IDF, token Jaccard, numeric street overlap, postal code matching, country validation).
3. Evaluates candidates using a trained gradient-boosted decision tree (LightGBM) to produce calibrated match probabilities in $[0.0, 1.0]$.
4. Streams scored pairs with strictly preserved ordering and pair IDs directly to Member 4 for clustering and graph resolution.
5. Provides a bounded-memory training data preparation workflow that aligns candidate pairs with Member 1's ground truth, guarantees 100% true-positive match preservation, and performs deterministic per-entity negative sampling without Source 1 data leakage.

```
+---------------------+       +-----------------------+
|  Member 1 Normalized|       |   Member 2 Candidate  |
|  Records (SQLite DB)|       |   Pairs (TSV stream)  |
+----------+----------+       +-----------+-----------+
           |                              |
           +--------------+---------------+
                          |
                          v
         +---------------------------------+
         | Member 3: Pairwise Matching     |
         | - Bounded-batch record join     |
         | - 12-Feature Pipeline           |
         | - LightGBM Probability Predict  |
         +----------------+----------------+
                          |
                          v
         +---------------------------------+
         | Scored Candidate Stream (JSONL) |
         | -> Delivered to Member 4        |
         +---------------------------------+
```

## 6. Training Data Preparation Workflow & Dry Run

Member 3 includes a streaming, memory-bounded CLI (`prepare_training_data.py`) to prepare pairwise training and validation datasets from Member 2's candidate stream and Member 1's ground truth.

### CLI Usage
```bash
# Run safe, read-only dry run (computes exact pair counts, memory profile, without writing data)
python -m business_entity_resolution.matching.prepare_training_data \
  --candidates data/candidate_train.tsv \
  --lookup data/entity_lookup.sqlite3 \
  --ground-truth data/train_ground_truth.tsv \
  --split data/validation_split.json \
  --negative-ratio 10 \
  --dry-run

# Execute actual preparation writing to JSONL
python -m business_entity_resolution.matching.prepare_training_data \
  --candidates data/candidate_train.tsv \
  --lookup data/entity_lookup.sqlite3 \
  --ground-truth data/train_ground_truth.tsv \
  --split data/validation_split.json \
  --output data/prepared_training_pairs.jsonl \
  --negative-ratio 10 \
  --seed 42
```

### Dry Run Guarantees & Features
- **Deterministic Negative Sampling**: Negative candidates per Source 1 entity are deterministically sampled using `seed + "-" + source1_id`. True positives are never dropped ($100\%$ preserved).
- **Zero Leakage**: Source 1 entities strictly partitioned into train or validation sets.
- **Unsampled Validation**: Validation candidate pairs are kept unsampled ($100\%$ preserved) to reflect true production deployment distribution.
- **Memory Scaling Audit**: Bounded streaming during candidate preparation ($< 50$ MB RAM). Reports memory breakdown for subsequent model fitting.

## 7. Interface Contracts

### 7.1 Input Contract from Member 1 (Normalized Records & Split)
1. **Normalized Tables / SQLite Index**:
   - SQLite DB (`entity_lookup.sqlite3`) with table `entities(entity_id TEXT PRIMARY KEY, source_id TEXT, row_offset INTEGER, payload BLOB)`.
   - Fields: `entity_id` (`S1-...`, `S2-...`, `S3-...`), `business_name_normalized`, `address_normalized`, `postal_code_normalized`, `country_normalized`.
2. **Ground Truth TSV** (`train_ground_truth.tsv`):
   - Header: `source1_entity_id\tmatched_entity_ids` (where `matched_entity_ids` is JSON array, e.g. `["S2-101", "S3-202"]`).
3. **Entity Split** (`validation_split.json` or `validation_membership.tsv`):
   - JSON: `{"train_source1_entity_ids": [...], "validation_source1_entity_ids": [...]}`.
   - TSV: `source1_entity_id\tsplit` (`train` or `validation`).

### 7.2 Input Contract from Member 2 (Candidate Pairs)
1. **Candidate TSV Format** (`candidate_pairs.tsv` / `candidate_train.tsv`):
   - Grouped TSV format:
     - Columns: `source1_entity_id\tcandidate_entity_ids` (JSON array of candidate IDs).
     - Optional metadata: `source1_row_index`, `candidate_rank`.
   - Pairwise stream adapter `Member2TSVAdapter` automatically unrolls rows into discrete candidate pairs while tracking deduplication and generating unique deterministic `pair_id` strings (`s1_id#target_id`).

### 7.3 Output Contract to Member 4 (Probability-Scored Stream)
Member 3 emits candidate pairs with calibrated probabilities in streamed JSONL (or TSV) format:

**JSONL Schema**:
```json
{
  "pair_id": "S1-100190437#S2-725882042",
  "source1_id": "S1-100190437",
  "target_source": "S2",
  "target_id": "S2-725882042",
  "probability": 0.043512,
  "source1_row_index": 0,
  "candidate_rank": 1
}
```

**Contract Invariants Guaranteed for Member 4**:
- Exactly 1 record emitted per input candidate pair.
- Output order strictly matches Member 2's candidate stream ordering.
- `probability` is a float strictly bounded within $[0.0, 1.0]$.
- Never contains `NaN`, `null`, or out-of-bounds probability values.
- Streamed line-by-line so Member 4 can consume without unbounded RAM buffering.
