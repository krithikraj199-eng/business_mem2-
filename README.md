# Member 3: Pairwise Matching & Classification

## 1. System Responsibility & Overview
Member 3 is responsible for the **pairwise matching and classification engine** within the Business Entity Resolution pipeline.

Given candidate pairs generated by Member 2's blocking mechanism and normalized entity records indexed by Member 1, Member 3:
1. Performs disk-backed joins between Source 1 records and candidate targets (Source 2 / Source 3) with bounded RAM usage.
2. Extracts a deterministic 12-feature similarity representation (string distances, character n-gram TF-IDF, token Jaccard, numeric street overlap, postal code matching, country validation).
3. Evaluates candidates using a trained gradient-boosted decision tree (LightGBM) to produce uncalibrated raw predicted match probabilities in $[0.0, 1.0]$.
4. Streams scored pairs with strictly preserved ordering and pair IDs (`source1_id::target_id`) directly to Member 4 for clustering and graph resolution.
5. Provides a bounded-memory training data preparation workflow that aligns candidate pairs with Member 1's ground truth, guarantees 100% true-positive match preservation, and performs deterministic per-entity negative sampling without Source 1 data leakage.

```
+------------------------------------+       +------------------------------------+
|  Member 1 Normalized TSV Records   |       |    Member 2 Candidate Pairs TSV    |
|  & SQLite Byte-Offset Index        |       |    (comma-separated candidate IDs) |
+-----------------+------------------+       +-----------------+------------------+
                  |                                            |
                  +---------------------+----------------------+
                                        |
                                        v
                       +---------------------------------+
                       | Member 3: Pairwise Matching     |
                       | - Bounded-batch record join     |
                       | - 12-Feature Pipeline           |
                       | - LightGBM Probability Predict  |
                       +----------------+----------------+
                                        |
                                        v
                       +---------------------------------+
                       | Scored Candidate Stream (JSONL) |
                       | -> Delivered to Member 4        |
                       +---------------------------------+
```

## 6. Training Data Preparation Workflow & Dry Run

Member 3 includes a streaming, memory-bounded CLI (`prepare_training_data.py`) to prepare pairwise training and validation datasets from Member 2's candidate stream and Member 1's ground truth.

### CLI Option Reference (`python -m business_entity_resolution.matching.prepare_training_data --help`)
- `--candidates CANDIDATES`: Member 2 candidate TSV path (required)
- `--lookup LOOKUP`: Member 1 SQLite index path (`entity_lookup.sqlite3`) or normalized data directory (required)
- `--ground-truth GROUND_TRUTH`: Member 1 ground truth TSV path (required)
- `--saved-split SAVED_SPLIT`: Member 1 `validation_split.json` or `validation_membership.tsv` path (required)
- `--output OUTPUT`: Destination JSONL path (required unless `--dry-run` is set)
- `--dry-run`: Perform read-only audit: report counts, size, and memory requirements without writing files
- `--negative-ratio NEGATIVE_RATIO`: Max negatives per positive (default: 10)
- `--max-zero-match-negatives MAX_ZERO_MATCH_NEGATIVES`: Max negatives for zero-match entities
- `--seed SEED`: Random seed for deterministic sampling (default: 42)
- `--batch-size BATCH_SIZE`: Lookup batch size (default: 1024)
- `--collection-aware`: Export full postal code collections
- `--overwrite`: Allow overwriting existing output file

### CLI Usage Examples
```bash
# Run safe, read-only dry run (computes exact pair counts and memory profile without writing files)
python -m business_entity_resolution.matching.prepare_training_data \
  --candidates data/candidate_train.tsv \
  --lookup data/lookup/entity_lookup.sqlite3 \
  --ground-truth data/train_ground_truth.tsv \
  --saved-split data/validation_split.json \
  --negative-ratio 10 \
  --dry-run

# Execute actual preparation writing to JSONL
python -m business_entity_resolution.matching.prepare_training_data \
  --candidates data/candidate_train.tsv \
  --lookup data/lookup/entity_lookup.sqlite3 \
  --ground-truth data/train_ground_truth.tsv \
  --saved-split data/validation_split.json \
  --output data/prepared_training_pairs.jsonl \
  --negative-ratio 10 \
  --seed 42
```

### Dry Run Guarantees & Features
- **Deterministic Negative Sampling**: Negative candidates per Source 1 entity are deterministically sampled using `seed + "-" + source1_id`. True positives are never dropped ($100\%$ preserved).
- **Zero Leakage**: Source 1 entities strictly partitioned into train or validation sets.
- **Unsampled Validation**: Validation candidate pairs are kept unsampled ($100\%$ preserved) to reflect true production deployment distribution.
- **Memory Scaling Audit**: Bounded streaming during candidate preparation ($< 50$ MB RAM). Reports memory breakdown for subsequent model fitting.

## 7. Interface Contracts

### 7.1 Input Contract from Member 1 (Normalized Records & Split)
1. **SQLite Byte-Offset Index** (`entity_lookup.sqlite3`):
   - Member 1 builds a byte-offset index SQLite database with the following tables:
     - `metadata (key TEXT PRIMARY KEY, value TEXT NOT NULL)`: records `schema_version`, `data_dir`, `source_columns`, `encoding`, `newline_mode`.
     - `source_files (source TEXT PRIMARY KEY, filename TEXT NOT NULL, file_size INTEGER NOT NULL, mtime_ns INTEGER NOT NULL, sha256 TEXT NOT NULL)`: SHA-256 fingerprint of each source file.
     - `entity_index (entity_id TEXT PRIMARY KEY, source TEXT NOT NULL, byte_offset INTEGER NOT NULL)`: mapping entity ID to file source (`source1`, `source2`, `source3`) and exact byte offset in the TSV.
     - Index: `idx_entity_source ON entity_index(source)`.
2. **Normalized TSV Files** (`normalized_source1.tsv`, `normalized_source2.tsv`, `normalized_source3.tsv`):
   - Each row contains exactly the **11 canonical columns** defined in `SOURCE_COLUMNS`:
     1. `entity_id`: e.g. `S1-100190437`, `S2-725882042`, `S3-998746725`
     2. `business_name`: raw business name
     3. `business_address`: raw street address
     4. `country`: raw country
     5. `business_name_normalized`: lowercase cleaned name
     6. `business_name_tokens`: whitespace-tokenized name tokens
     7. `business_address_normalized`: lowercase cleaned address
     8. `address_tokens`: whitespace-tokenized address tokens
     9. `address_numbers`: extracted street numbers
     10. `postal_codes`: postal code or collection of postal codes
     11. `country_normalized`: normalized ISO country representation
3. **Ground Truth TSV** (`train_ground_truth.tsv`):
   - Two columns: `source1_entity_id\tmatched_entity_ids` (where `matched_entity_ids` is JSON array format, e.g. `["S2-101", "S3-202"]` or `[]`).
4. **Entity Split** (`validation_split.json` or `validation_membership.tsv`):
   - JSON: `{"train_source1_entity_ids": [...], "validation_source1_entity_ids": [...]}`
   - TSV: `source1_entity_id\tsplit` (`train` or `validation`).

### 7.2 Input Contract from Member 2 (Candidate Pairs)
1. **Candidate TSV File** (`candidate_pairs.tsv` / `candidate_train.tsv`):
   - Two-column TSV format:
     - Column 1: `source1_entity_id` (e.g. `S1-100190437`)
     - Column 2: `candidate_entity_ids`: **comma-separated candidate list** (e.g. `S2-725882042,S3-998746725`). Empty string if no candidates.
   - Streamed and expanded by `Member2TSVAdapter`:
     - Expands candidate lists into individual candidate pairs in input order.
     - Derives `candidate_source` from prefix (`S2-` -> `source2`, `S3-` -> `source3`).
     - Tracks duplicates using SQLite disk-backed edge tracker (`_DiskEdgeTracker`) or in-memory tracker.
     - Retains candidate provenance: `source1_row_index` (row index of Source 1 in TSV) and `candidate_rank` (index within candidate list).
2. **Deterministic `pair_id` Delimiter**:
   - `pair_id` is generated deterministically using double-colon `::`:
     ```python
     def generate_pair_id(source1_entity_id, candidate_entity_id):
         return f'{source1_entity_id}::{candidate_entity_id}'
     ```
     Example: `S1-100190437::S2-725882042`.

### 7.3 Output Contract to Member 4 (Probability-Scored Stream)
Member 3 outputs candidate pairs with uncalibrated raw LightGBM predicted match probabilities in streamed JSONL (or TSV) format:

**JSONL Schema**:
```json
{
  "pair_id": "S1-100190437::S2-725882042",
  "source1_id": "S1-100190437",
  "target_source": "S2",
  "target_id": "S2-725882042",
  "probability": 0.043512,
  "source1_row_index": 0,
  "candidate_rank": 0
}
```

**Field Specifications**:
- `pair_id` (`str`): Unique candidate pair identifier using double-colon (`source1_id::target_id`).
- `source1_id` (`str`): Source 1 entity identifier (`S1-...`).
- `target_source` (`str`): Target source system identifier (`'S2'` or `'S3'`).
- `target_id` (`str`): Target candidate entity identifier (`S2-...` or `S3-...`).
- `probability` (`float`): Raw LightGBM predicted probability strictly in $[0.0, 1.0]$. Note: this is an **uncalibrated** model score.
- `source1_row_index` (`int`, optional provenance): Zero-based row index of the Source 1 entity in Member 2's candidate TSV.
- `candidate_rank` (`int`, optional provenance): Zero-based rank of the candidate within that Source 1 entity's candidate list.

**Contract Invariants Guaranteed for Member 4**:
- Exactly 1 scored record emitted per input candidate pair.
- Output stream order strictly matches Member 2's candidate stream ordering.
- `probability` is a float strictly bounded within $[0.0, 1.0]$ (never `NaN`, `null`, or infinite).
- Streamed line-by-line so Member 4 can consume without unbounded RAM buffering.
